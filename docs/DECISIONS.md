# Decisions

The owner's decisions, dated, one line each; and the design decisions that shaped the code. **Not reopened
without a new fact.** Collected 2026-10-09 from the former `ARCHITECTURE.md` (its Decisions table and its
sections' *(owner, date)* marks, now in [history/](history/README.md)), from [findings.md](findings.md) and
its [archives](history/README.md), and from CLAUDE.md. The longer reasoning is in the findings row or the
history section named. The rules these produce are in [INVARIANTS.md](INVARIANTS.md).

## Architecture and process

| Date | Decision |
|---|---|
| 2026-09-23 | One owner per concern, each with a guard test; three kinds of data (file copies, decisions, derived) with one writer each; a photo has an integer id and its path is an attribute. |
| 2026-09-23 | The web layer is Flask and Waitress. One server process serves both apps, on the ports they used (8090 TagPup, 8080 TagTuner). |
| 2026-09-23 | `Library` and `Result` live in `core` (plain values every layer passes along). |
| 2026-09-24 | One composition root, `tagpup.runtime`; the layers stay as they are (letting `ml` read `config`, merging the infrastructure layers, ports-and-adapters throughout were weighed and rejected). A service that uses a model is given it. |
| 2026-09-24 | A service that reads returns what it read and raises `NotFound` (404) or `Refused` (400); opening a photo, Explorer and the folder dialog stay web routes. |
| 2026-09-24 | Five maintenance scripts retired; every index entry whose file was gone dropped; a new library is seeded with one face root, People, which cannot be taken away. |
| 2026-09-24 | The two servers are two Flask apps from one factory, one per port; the sockets are bound with `SO_EXCLUSIVEADDRUSE`. |
| 2026-09-25 | The pages are ES modules (`web/tagpup/`, `web/tuner/`, `web/common/`) with no build step; page tests load modules into jsdom in import order, each in a scope of its own. |
| 2026-09-25 | The MCP server names a library in every call; it has no library of its own (#100); its reads are `services.inspect`. |
| 2026-09-25 | Bulk edits and migrations are recorded in a journal, per changed column, applied and undone only where rows are what the change expects, rehearsed by a rolled-back dry run. Full backups only for destructive migrations. SQLite's session extension was weighed and its semantics copied, not the library. |
| 2026-09-25 | A library's settings live in the library, changed from TagTuner's gear through the journal; `config.ini` is retired; the data folder is fixed (`TAGPUP_HOME/data`). Settings with consequences are locked behind a Change... that asks for each consequence. From 2026-10-09 nothing reads `config.ini` (a library holding no settings gets the defaults; an old file is ignored and left on disk). |
| 2026-09-25 | Input rules have one owner, `tagpup.core.validation`; output is escaped by building elements from text. |
| 2026-09-25 | Each library keeps three daily, one weekly and one monthly snapshot; it is a read transaction and holds no writer back (amended 2026-09-26). |
| 2026-09-25 | Recurring operations are registered in `tagpup.jobs.recurring` and run by one runner in the web process; no Windows Task Scheduler. The CLI runs one by hand; the MCP server runs none (#334, 2026-09-26). |
| 2026-09-25 | The server and jobs run as one always-on process started at login from the Startup folder, not as a Windows service. Idle models are released. |
| 2026-09-26 | Event-driven first: work that follows an event runs at once or is queued; a schedule is only for safety, retention and catch-up. |
| 2026-09-26 | The server answers this PC only (127.0.0.1 and ::1) until phase 10 adds logins; `--listen lan` is for then. |
| 2026-09-26 | Each library has root folders and ignored folders (settings, TagTuner's gear); the idle registry releases the photo indexes too (#345, #362). |
| 2026-09-28 | The retro: a worker's brief names how the work fails (interrupted, two at once, a read that fails, the real data, what the owner sees); TagPup shows its write queue bottom-right (#387, #406). |
| 2026-10-02 | The stored path is root-relative (`@root/relative`), not a relocate alternative; **nothing converts a library unasked** (`roots adopt` is explicit). |
| 2026-10-02 | A journaled change stays undoable across an ADDITIVE migration that touches no table a change can name; any other migration since blocks the undo. |
| 2026-10-02 | Just-look reverses the 2026-09-28 rule that a refused write refuses the request (#527). Automatch is not journaled; no journal polish until the major changes are done (#639). |
| 2026-10-04 | Stabilize before new features: review every open finding and fix small issues first. An update must hand over without killing (#726). |
| 2026-10-07 | Sandboxes that load models share the owner's card lock; a server the install starts has no window (#799, #801). |
| 2026-10-09 | **A feature freeze.** Allowed: deletion, simplification, docs, test speed, bug fixes for what the owner hit, installing what is merged. A branch is about 1,200 lines, one concern; at most two review rounds; severity `data` / `wrong` / `low`, only the first two block a merge; one migration in flight; a new feature states its live count (under about 20, a one-off script); each branch removes as many concepts as it adds. |

## People, names and tags

| Date | Decision |
|---|---|
| 2026-09-23 | A person is a leaf tag; the tag is a path (`People/Name`), the identity the leaf. Six faces both excluded and named kept their names (#3). |
| 2026-10-02 | Identity by id: faces and `photo_people` carry the tag node's id; `name` is a cache of it. |
| 2026-10-04 | **A branch is never a person**: a group of people (Family/Thackeray) is not tagged as a person, and a tag used on photos gets no children; both enforced as refusals with an explanation (2026-10-04, 2026-10-07; #660). |
| 2026-10-04 | Dates "Other" row = the year's photos with no month (#685); keep counting photos in the People tab for now (#686). |
| 2026-10-07 | The AI pipeline: plumbing changes first; replace the face models (insightface; the non-commercial licence is accepted) keeping the old vectors beside the new; replace CLIP (SigLIP 2) with embeddings versioned by model; search by what is in the picture; bake the CURRENT model's vectors and the face regions (MWG) into the photo's XMP. |
| 2026-10-07 | The sideways-photo (orientation 5-8) redesign is un-tabled: boxes stored as the photo displays; rotation done outside TagPup is detected by a fingerprint; every detected face is written, an excluded one removed; a small subset first, no full dry run. |
| 2026-10-07 | People by id stage 2: the 4 names with no person tag get the tag created; a name matching two tags is confirmed by name before anything is written; deleting a person tag faces use refuses unless forced; old history is translated to stay undoable. |
| 2026-10-09 | Names on a group tag, or with no person tag, are **not unnamed on their own**: they are listed for the owner to decide (names to review), possibly linking the name to a person in another library. Every recommendation of the people-by-id design accepted as written. |
| 2026-10-09 | The backfills `tags-from-faces` and `faces-from-tags` take `--folder` (#994). |
| 2026-10-11 | The CLI commands `faces-from-tags`, `settings` (and `settings set`) and `jobs` (and `jobs run`) are deleted ("I never use these from the command line"). Their forms in the pages stay: Name faces from tags, the gear dialog, the Activity page. #994's `--folder` form of `faces-from-tags` went with the command (the dialog's "Only this folder" stays); `tags-from-faces --folder` is untouched. |

## Folders, roots and markers

| Date | Decision |
|---|---|
| 2026-10-02 | Roots: no cross-process lock between the server's Suggest and a CLI index or sync; rows spelled by the share address while the root is a drive refuse the whole adoption, the dry run naming them (#448). |
| 2026-10-08 | A folder gone from disk whose parent is there is the unit followed; **a ghost (a gone folder with no rows under it) is only reported**, never followed (#919, #925, #934). |
| 2026-10-08 | Folder ids: a hidden `.tagpup` file in each leaf folder holding a library's id and its UUID for the folder; relinking by the marker is exact and automatic, per library; `relink-folders` does not mark a folder it followed; written only by an explicit command. |
| 2026-10-08 | Truncated JPEGs stay refused, not read (#415). |

## Keeping the project small (2026-10-09 / 2026-10-10)

| Date | Decision |
|---|---|
| 2026-10-09 | A feature freeze, and the rules of CLAUDE.md "Keeping the project small": branches of about 1,200 lines or fewer, at most two review rounds, a severity on every finding (only `data` and `wrong` block), one migration in flight, a new feature states its live count, each branch removes as much as it adds. |
| 2026-10-10 | One-offs are fixed by hand and flagged, not auto-corrected: a case affecting about 5-20 photos gets a check that lists them (counts by default, names behind the reveal rule), not repair code with special conditions and tests. |
| 2026-10-10 | A person's id represents the ENTIRE TAG PATH (the model of Windows Live Photo Gallery). The leaf name is never identity; the shared-leaf case (a pet and a person under different roots) was an early design mistake, fixed by hand. Tagging by typing a name stays: it resolves to a path, and two matches ask "which one?" by path. Supersedes the 2026-10-09 short-label-when-shared design. |
| 2026-10-11 | The same name under different paths (the pet and the person called alike) is NOT a scenario to handle: they are two people with two ids. No doctor flag, no special case: the doctor does not report 'people sharing a leaf' or 'names with several person nodes'. A typed bare name that matches two paths simply asks which one (the picker), as for any ambiguous choice. |
| 2026-10-10 | Folder markers (`.tagpup`) are deleted end to end: sync keeps its name/size/time pairing; a folder renamed and re-saved before the next sync is flagged missing and renamed back by hand. Reverses 2026-10-08. |
| 2026-10-10 | Names to review: the acting UI is replaced by the doctor's list once the owner has settled the names by hand. **Superseded the same day by the next row.** |
| 2026-10-10 | EVERY TAG HAS AN ID: a face name or a file keyword that has no node gets a node when it is first seen -- a node directly under the tree's root for a bare name, its own path for a keyword -- so there is no 'unresolved name' state and no id-less row. There is no special 'rootless' kind (owner: the root is just the top-level node above all child nodes): a top-level node is an ordinary node, and the rule 'a person cannot be a top-level node' is dropped (a person is a node marked as a person with no node under it, wherever it sits). The owner views these in the tag view and merges them into the right branch with the existing tag merge (which moves faces and photo lists by id). A one-time command (dry run first) creates the nodes for today's names and keywords. The names-to-review service, routes and dialog are deleted; the doctor lists top-level people not filed in a branch. Reverses 'indexing never adds to the tree'. |
| 2026-10-10 | Camera search table (`search_gear`) and `photo_meta` are dropped with migration 30; a camera search scans the stored metadata. |
| 2026-10-10 | The big photo_index library is archived out of `data/` (snapshot first; kept as a scale-test copy). |
| 2026-10-10 | Machinery with zero live use is deletion-first, each deletion its own small branch, taken in the domain registers' order (untracked reports/One-off register - *.md): `relink-folders`, `reread-fields`, `dedupe-spelled-rows`, `backfill_document_ids`, journal prune, name-only face replay, `legacy_counters`, `faces_pending`. The resumable bulk-edit job, roots adoption/Verify, damaged-photo handling and the legacy read-only CLI commands wait for the owner's yes, one at a time. The Activity file-access probes got it on 2026-10-11 and are deleted. |
| 2026-10-11 | The supervisor (the always-on process, `tagpup.supervisor`, its Startup shortcut script and tests) is deleted: it ran once (2026-09-26 to 10-02); launches and installs hand a server over themselves (`tagpup.launcher`). The Activity page no longer shows a supervisor card. |
| 2026-10-11 | Roots adoption is deleted end to end: `roots adopt`, `roots repair-address`, the adoption service and store module, and the undo of their journal changes. All three live libraries are already adopted (live count: 3 of 3, adoption has run); the code had no further use. Kept: `roots check`, the root-relative stored paths, `machine_roots.json`, `@name/rel` resolution, the journal's reading of pre-adoption native values, Change location. History still lists the old `roots adopt` changes; their undo is refused with a sentence (the copy taken before is the way back). The Verify dialog, the full-run verification job and Change back in the Roots dialog are the next deletion (done 2026-10-11, the owner's yes: Verify, Verify all and Cancel, `tagpup.jobs.verifying`, the full walk of `roots_verify`, `last_verify`, `/api/roots/verify`, `/verify-cancel`, `/change-back`, `Machine.change_back`, `config.change_back`; Change location keeps its dry run, which is a sample of the new place). |
| 2026-10-11 | The damaged-photo handling is deleted (owner: yes; its live count was 0 rows in all three libraries): the `damaged_files` table's use, Activity's Needs attention, the headers' badge, the folder notice and the cards' marks, Check again, `/api/damaged-photos*`, `/api/folder/damaged` and `/api/activity/attention*`. A photo whose file stops short is still never written to (2026-10-08, "Truncated JPEGs stay refused, not read"), but asked of the file by each write, not remembered; `tools/doctor.py` counts the photos whose file fails to open. `damaged_files` and `faces_pending` stay as tables nothing writes, until a migration drops them. |
| 2026-10-11 | The CLI commands `remove` and `index-faces` are deleted (owner): the library is kept in step by sync and Name faces, faces are detected by the indexer and Suggest, and neither command was journaled. The rest of the CLI is reviewed for overlap with the UI; a command goes only when the UI has all of it, nothing documented points at the CLI form, and its live use is zero. |
| 2026-10-11 | A bulk edit of a library view's selection is one synchronous request, not a job: `POST /api/library/bulk-edit`, at most 5,000 photos ("a 5,000 cap, and simplify it and make it synchronous"), one journaled change under the lock of changes of photo files, a busy message with the count while the page waits, no progress, cancel, polling or Activity entry. The job (`tagpup.jobs.bulk_edits`, the strip's Cancel and Start again, `/api/library/bulk/*`) is deleted; the `job_runs` rows it wrote stay and are listed by Activity. |
| 2026-10-11 | ONE BATCH MODEL (owner approved; merge 2, the server side): a batch of photo files is the journaled change `write_fields` plans, its files' states its progress, no new table or thread, the request synchronous. More than 25 photos is a batch: one at a time in a process (a second waits its turn, eight at most, then it is refused saying how many are ahead; a waiting one is lost by a restart), written 25 files a chunk with the lock of changes of photo files let go between chunks, stopped by Cancel or a hand-over at a chunk (what it wrote is applied and undoable). Cap 5,000 photos for every writer EXCEPT the tag tree's rewrites (rename, delete, merge, a person's rename), which have none ("as long as there is progress and cancel"). A hand-over stops a batch at its chunk; the person starts it again and History undoes it. Face assignments fold into the model next. |
| 2026-10-11 | FACE ASSIGNMENTS ARE A BATCH (owner approved "face reassignments: accept"; merge 4 of the batch model): Assign, Unmatch, Exclude selected, Ignore cluster and Re-examine are one journaled change of photo files whose faces are written in the transaction that marks each photo's file done, so file and faces cannot disagree, a crash is settled forward with both, and History's undo restores both. DROPPED, by the owner: Resume of a stopped assignment and the Undo of a whole job (`/api/faces/job/*`, the banner offering them, the plan and state files of the cache folder, the `assign faces` rows of `job_runs`): a batch stopped by Cancel or a hand-over is asked for again; the Undo bar of Identify Faces undoes the change through History's route. Seen differently: a photo whose tag cannot be taken off keeps its face named (it used to be unnamed with the tag left); a photo whose file is not there is not named (it was, when the index already said it held the person); more than 5,000 photos to look at are refused, nothing changed. |
| 2026-10-11 | ONE BATCH MODEL, merge 3 (the page): one strip for the batches of photo files on TagPup and TagTuner (`web/common/batch-strip.js`) replaces the bulk edit's strip, its "writing the files takes N minutes" sentence and the tag editor's "slow after 30 s / stuck after 5 minutes" notices; progress is the server's counts, never a guess. The photo write queue box (a single save's "Saving 2 of 5", Retry, Dismiss) is kept: its Retry carries the text of a failed save and is not a batch. Activity keeps its own rows. |
| 2026-10-11 | A page test may run against the real apps instead of a hand-written fake (owner approved; allowed under the freeze only because it deletes as many test lines as it adds): `tests/page_server.py` starts both apps over a home of the test's own on ports the system chooses, `tests/test_pages_against_the_real_server.py` seeds a library per node test with the code that makes the real rows and runs the node file (`tests/frontend/harness.mjs`: `realLibrary`, `RealServer`, `until`, which waits on replies and not on time). A flow so covered deletes its fake copy; a failure the real server cannot be made to give stays scripted. Closes contract rows 12 and 22 for the four flows converted, not for the files that still use a fake. |
| 2026-10-11 | MIGRATION 32 (owner approved; the only migration in flight): drops `tag_taxonomy.is_people` (unread, unwritten; `photo_index` only) and folds `sync_runs` into `job_runs` (a sync is a run of `sync-whole` or `sync-folder`; the newest whole sync in step per library is kept, the other records dropped, the syncs' changes stay in the journal); `schema.COLUMNS_DROPPED` keeps every older change undoable. A sync of one folder is recorded only when it found, changed or queued something, or ends a stretch of not being in step. |
| 2026-10-11 | A SPECIAL CASE NEEDS A REAL INSTANCE: a fallback, compatibility arm or defensive branch is written only for a case with a live count above zero or a named user action that makes it; otherwise the write that could make it is refused at the source. Gates: a CLAUDE.md rule, a question in tagpup-worker, defect class 9 in tagpup-reviewer, a line in each owner charter. Reason: three imagined cases (a name two people share, a group's name, a keyword equal to a person's name) had grown into a whole name-keyed fallback beside the id; the owner ruled all three out and identity is the id only. |
