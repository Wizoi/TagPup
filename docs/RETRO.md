# The retrospective

How a retro of AI-assisted work runs on this project: one owner, a main session, many agents. Its object is the
system (instructions, guards, briefs, the review loop, the shape of the sessions), never "the model". It runs on the
record that already exists (git, the findings ledger, DECISIONS.md, the usage fields of the session transcripts) and
ends in at most three changes, each enforced by something other than an agent's goodwill and each with a metric that
says at the next retro whether it worked. The research behind it: `research_notes/ai-dev-retrospectives.md`
(untracked), sections 3 to 6. The retros themselves are in [retros/](retros/README.md).

## When

- **At each phase end**, in a fresh session (`/clear` first: a retro must not run on the long context of the work it
  judges). About 60 minutes of the owner's attention.
- **On a trigger**, a retro of the one episode, about 20 minutes:
  - a defect the owner hit (in the installed app, or a number told to them that was wrong);
  - a third review round on one branch;
  - a branch merged above its size budget (about 1,200 lines);
  - a session that hit the usage limit;
  - a rule broken twice (two findings citing the same rule of CLAUDE.md or INVARIANTS.md).

## Who does what

- **The owner decides**: the question, which episodes matter, the actions. Nothing else in the retro is a decision.
- **Agents gather**: the main agent runs the metrics script and builds the timeline. Counts only, no judgement.
- **A fresh-context agent drafts the insights**, one that did none of the work, given only the data file, the
  findings ledger, DECISIONS.md and this file. Not the transcripts, not the conversation.
- **The main agent never grades its own work**, the retro included: it records and proposes the instruction diff.

## The five phases

| Phase | Steps | Inputs | Output | Time | Who |
|---|---|---|---|---|---|
| 1. Set the stage | Fix the window (dates or a commit range of the trunk), the one question ("what cost the most, and what would have been cheaper?"), the triggers that fired. State the blameless rule. | The last retro's actions and their metrics | A paragraph of scope | 5 min | Owner; main agent writes it |
| 2. Gather data | Run `tools/retro_metrics.py --since <date> --until <date>` into `reports/retro-<date>-data.md` (untracked). Add the timeline: merges, reverts, findings opened and closed, decisions, compactions, restarts. | git, `docs/findings.md` and `docs/history/findings_closed_*.md`, DECISIONS.md, transcript usage fields, the instruction files | The data file: tables, no interpretation | 15 min | Main agent |
| 3. Generate insights | The three most expensive episodes by cost or escape. For each: the timeline; what the agent's context and brief held; the earliest signal; "how" questions, not five whys; the cheaper path with what was known then; the single place that should own the rule. | The data file only (plus the ledger, DECISIONS.md, this file) | Episode notes and up to three proposed actions | 15 min | Fresh-context agent drafts; owner corrects |
| 4. Decide | At most three actions, each one of the four kinds below, each with its metric and target for the next retro. Check the last retro's actions against their metrics. | Episode notes; last retro's actions | Actions in DECISIONS.md (dated, the owner's words); findings rows for code changes | 10 min | Owner decides; main agent records |
| 5. Close | The instruction diff: remove what a guard now enforces, every stale number, every rule nothing breaks; then add the actions. Write the retro document; update the memory handoff; `/clear`. | CLAUDE.md, the agent definitions, memory | `docs/retros/<date>-<scope>.md`; a net-zero or net-negative instruction diff | 5 min | Main agent proposes; owner approves |

## The rules of the process

- **The data file is regenerated by `tools/retro_metrics.py`, never edited by hand.** A number that is wrong is a bug
  in the script, fixed there and the file made again.
- **Every number is counted**, in this retro, from the data file or a read-only count. A number from an agent's report
  is a claim, not data (a relayed "38 folders, 13,816 photos" was 4 folders and 188 photos, 2026-09-28).
- **No action without a metric and a target for next time** ("rows citing the rule: 4 this window, 0 next").
- **At most three actions.** Each is one of:
  - **delete**: a rule, a mechanism, a shim, a branch with no instance;
  - **guard**: a test, a ratchet or a hook that fails when the rule is broken;
  - **brief change**: a line in an agent definition or a brief's standing list;
  - **no action**: the episode was the cost of learning (no earlier signal existed).
- **Blameless.** Causes are context, briefs and guards: the rule was buried, contradicted elsewhere, absent from the
  brief, or never enforced. "The model ignored it" ends the analysis and is not a cause.
- **A retro that adds rules removes at least as many lines of instructions** (the branch rule, applied to CLAUDE.md,
  the charters and memory).

## The metrics

`tools/retro_metrics.py` (`--since`, `--until`, `--json`) prints six sections. What each tells, and what it cannot
count (gather that by hand, or say "not counted"):

- **GIT**: merged outcomes in the window (merges into the trunk), not commits; reverts; lines added and removed by
  area. Commit and line counts are context, never success. Not counted: fix-of-a-fix.
- **FINDINGS LEDGER**: rows opened (by day and severity) and closed (by kind); the rows naming review or an owner (a
  proxy for review-found); rows closed obsolete or stale (ledger drift). Not counted: escapes to the owner, review
  rounds per branch, rows citing a rule (`tools/stale_findings.py` finds stale rows on the trunk).
- **TESTS**: test files and `def test_` at the start and end, files added and deleted, `Lifted:` lines. Not counted:
  unmapped files in `tests/owners.py` and the other ratchet counts.
- **CLAUDE CODE SESSION TRANSCRIPTS** (usage fields only, never message text): tokens, cache write and cache read by
  model and day; the calls above 150k of context; cost low..high at list prices.
- **AGENTS AND BRANCHES** (the subagent `.meta.json` files: agent type, worktree branch, stopped by the owner; never
  the description): TOKENS BY AGENT TYPE (runs, calls, tokens, share, cost) and review work (reviewers, quick
  reviewers, owners) against workers; TOKENS BY BRANCH (the top 15, and totals by state: merged, fast-forward,
  nothing to merge, open, no merge found, an upper bound of never merged); RUNS STOPPED BY THE OWNER; MAIN SESSIONS
  (count, average and largest context per call, compactions and the tokens before each).
- **WORKERS**: lines ADDED per merge against the 1,200 budget (added plus removed beside it, the old measure), each
  trunk merge's lines; `--branch <ref>` is the guard before a merge (exit 1 when it adds over the budget, unless
  `--allow-over`). Review rounds per branch are counted only for a review run whose transcript `cwd` is the branch's
  worktree (the tool falls back to it when the meta file names no branch); 144 of 146 reviewer runs counted on
  2026-10-17 started in the main checkout, so they tie to no branch (by design: say the branch in the brief, or start
  the reviewer in its worktree, if a retro needs the rounds).

Plus, by hand from the files: the lines and bytes of CLAUDE.md, each agent definition and MEMORY.md; rules with a
named guard against rules without; numbers in CLAUDE.md that no longer hold.

## Pitfalls

- **Hindsight bias.** The outcome makes the cheaper path look obvious. Ask what was known at the time and what the
  earliest signal was; add a rule only at a signal that existed. Otherwise it is "no action".
- **Agents grading their own work.** A model favours its own output, and agents can make tests pass rather than the
  code right. Gathering is separate from judging; the judge has a fresh context; claims are checked against the record.
- **Felt speed against measured speed.** The owner's sense of speed and an agent's "all green" are both unreliable
  (in one study, developers felt 20% faster and were 19% slower). Prefer the record.
- **Measuring what is easy.** Commits, lines, findings closed and tokens spent are easy because the tools emit them.
  Escapes and cost per merged outcome need a join; do the join.
- **Instruction bloat.** Every retro adding rules is the failure it is meant to fix: adherence falls as instructions
  grow. The target is CLAUDE.md under 200 lines per file; every retro's instruction diff is net-negative or zero.
- **Advisory prose against guards.** CLAUDE.md and the charters are advisory; a test, a ratchet or a hook is
  deterministic. A rule broken twice moves into a guard and keeps one line in CLAUDE.md that names it.
- **Reviewers asked for gaps find gaps.** Count the `low` rows that became code and ask whether they paid off.
- **Privacy.** Transcript text and brief descriptions can hold names from the libraries; the script reads only usage
  and meta fields, and the retro document holds no real names.

## The retro document

`docs/retros/<date>-<scope>.md`, listed in [retros/README.md](retros/README.md). Sections, in order:

1. **Scope and trigger**: the window, the question, the trigger or "phase end".
2. **Counted numbers**: from the data file, each with where it came from; nothing recalled.
3. **Timeline**: merges, escapes, decisions, restarts and compactions, dated.
4. **The three most expensive episodes**: for each, what it cost, the earliest signal, and the cheaper path with what
   was known then (or "none: the cost of learning").
5. **Did the last retro's actions work**: each action, its metric then and now, kept, rewritten or deleted.
6. **Actions** (at most three): kind, the change, the metric and its target.
7. **The instruction diff**: lines removed and added, per file, with the guard each removed line now relies on.
8. **What to carry to other projects**: what in this retro is not TagPup's alone.

## How it ends

The decided actions go into [DECISIONS.md](DECISIONS.md), dated, in the owner's words, with their metrics; a code
change is a findings row and a branch like any other. The instruction diff is committed on its own. The memory
handoff records the retro's date, its actions and where the document is. Then `/clear`: the next phase starts in a
fresh session.
