# Manage Folders: one gear item in TagPup and TagTuner adds a folder to the library or removes one
Live count: 3 libraries, 1 root each; added folders 20 (kr-track), 1,092 (photo_index, 1,064 added without subfolders), 8 (renton_parkrun) (read-only, 2026-11-19). TagPup's page has no folder management today beyond the "add the folder you opened?" question; TagTuner has two buttons ("Add folders", "Remove folder") and two modals.
Domains: Integration (routes, pages), Data (remove, added_folders), Files (index queue); integration reviews the seams

| Mechanism | The ONE place it lives | Its owner | New or existing |
| Add folders (record, then queue the index) | `tagpup/services/libraries.py::add` through ONE `index-start` route taking `folder_paths` | Data / Files | existing: the two apps' copies become one |
| Remove a folder (rows, faces, thumbnails; ignored if a parent covers it) | `tagpup/services/faces.py::remove_folder` through `POST /api/folder/remove` | Data | existing: route moves |
| The list the dialog shows | `photos.indexed_folders` via `/api/folder/indexed` (one list, with a filter box) | Data | existing |
| The six folder routes for both apps | new `tagpup/web/folder_routes.py` registered in `app.py` for both (indexed, remove, subfolders, index-start, index-active, index-cancel) | Integration | new: moved from `tuner_routes.py` |
| The dialog both pages open | new `web/common/folder-manager.js` + `.css`, built like `web/tuner/roots.js::buildRootsDialog`; ported from `web/tuner/indexing.js` (picker 182-341, remove list 348-456); each page passes `queued(folders)` and `removed(folder)` | Integration | new (the tuner's modals and buttons are deleted) |

Decisions (the plan's, not reopened): the gear item is `data-action="manage-folders"` in both pages; TagTuner's "Add folders" and "Remove folder" buttons, their two modals, styles and three page tests go; its header progress bar stays. A folder removal stays NOT journaled and NOT undoable (as today; the dialog says the files stay and the face work goes); making it journaled is a Data decision, not this feature. The dialog never touches `roots` (TagTuner's Roots dialog stays).
Findings to fix with cut 1: `folder_remove` maps any exception to a hand-made 500 (contract row 12); `/api/folder/remove` is not refused while the folder (or one above it) is queued or being indexed (the running index then fails `NotHeld` on its next row; a server test first); `/api/folder/remove` MUST join `name_faces_routes.GUARDED` (it would otherwise delete photos a Name-faces job holds ids of: the one `data`-class risk; `tests/test_write_routes_are_classified.py` catches it).
Risks: `/api/folder/indexed` stats every added folder (1,092 on photo_index; bounded per look): measure it in a sandbox before TagPup opens it routinely; if slow, `on_disk` becomes lazy. A dialog cannot outlive its library (both pages reload on a library change); drop a late reply from the old library by token as `roots.js` does. Removing a child under a parent add puts it in the ignored folders (journaled): the dialog says so.

Steady-state writer: no data is written afterwards by a command; each add or removal is the owner's action through these routes.
One-offs: none.
