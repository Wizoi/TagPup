# Tag changes to photo files are queued once, per file, and folded into the next write; a photo with one waiting is read-only
Live count: bulk tag writes today are one POST /api/photos/bulk-tags per click over N paths (a second waits behind the whole first, no way to add to a running change); the single-photo panel has no pending state for a photo in a bulk (counted from the code, 2026-11-16; History row counts of bulk changes to be read-only counted by the cut-1 worker). Second tab / phone editing beside a bulk: live: 0 (owner's one browser; a second process is refused by the lock and the journal's planned rows).
Domains: Views (the page's pending map and the read-only panel), Files (the journaled write and what it refuses), Data (the group of changes in History and Undo), Integration (the route's reply contract); integration reviews the seams

Owners' consult 2026-11-16: all four REFUSE a running change that accepts appended ops (its plan, before/after per file, is committed up front; settle and undo read only that; ids order writes: #1937). A tag added later for a file already written is a NEW change, never a second pass inside one. Data would put the queue on the server; Views, Files and Integration put it on the page, and nothing needs the queue seen from a second tab. Decided: the page.

Steady-state writer: every tag change from the folder view or the panel enters `pending.js`; the server's one writer is `file_changes.write_fields` through `change_each`; no command run. The library view's bulk (`bulk-edit.js`, ids and a selection token, `bulk_edit.py:220` calling `change_tags`) is NOT folded in: a second key is a second map; the owner decides whether it wants coalescing there at all (its own merge, keyed by id).
One-offs: none.
Page closed or app handed over with ops pending: unsent ops are lost (memory only, as every unsent queue entry is today); `beforeunload` warns while the map is non-empty; a sent chunk is a normal change, settled by the file. A library switch and leaving a folder wait for the map to empty, or drop it when the owner leaves anyway; a chunk already out finishes, and its reply reaches the records this browser kept of the folder left. A drain stopped by Cancel drops the unwritten files' ops and says so; a failed chunk gives its files' ops back to the map once (the Retry entry), never loops. A hand-over mid-drain re-queues the files the reply did not name written.
Tests (scenarios): a tag added while 50 files drain reaches the files not yet sent in the same write (written once) and the written ones in a later chunk; remove-then-add; a chunk failing part-way; a save queued between chunks runs between them and every file ends with both the tag and the save; Undo of the group restores every file; a panel with a pending photo is read-only with the sentence.
Cuts, each leaving the trunk whole and under 1,200 lines (a deletion is never over budget), each deleting what it replaces:
1. Files + Integration (~300): `unsettled` covers a running change's planned files; `bulk-tags` sends `conflicts`; the page's bulk handler reads them (it marks every non-skipped target written today: a file that refused the tags is shown as holding them). Verify the loss with a test first (a single save during a 50-photo bulk); record a finding for what it shows.
2. Data + Integration (~300): the group token in `changes.summary`, the grouped History line, Undo of a group. Before the page makes many chunks per action (a 5,000-file bulk is 200 changes).
3. Views (~700): `pending.js`, the route takes `changes` (old body deleted), the read-only panel, write-queue wording ("Add 2 tags to 48 photos, 3 more pending"), `beforeunload`; `tags-off.js` folds in.
4. Optional, the owner's call: the library view's bulk by id.

Cut 3 token rules (owner confirmed 2026-11-16, from the cut 2 review #3067): the drain's group token is one `crypto.randomUUID()` per owner action per browser (36 characters, inside `GROUP_TOKEN`; a reused token merges two actions into one History line and one Undo); every chunk of the action carries it; a chunk that merges a later click's ops into "the files not yet sent" carries the FIRST action's token, and the History line then names both actions' tags (or the queue is kept per action: the cut 3 brief picks the smaller, and says so). A group is at most `batches.CHUNK` (25) photos a write. The History line's photo count sums the files each chunk wrote, so a file written by two chunks of one token counts twice; the cut 3 brief says whether that matters (wording only, #3067).
