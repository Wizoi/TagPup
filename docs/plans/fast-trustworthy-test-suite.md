## What the numbers say

The cost is in test **setup**, not in the checks. Real ExifTool runs per photo in every `setUp` (63 files, 1,861 s, about
half of all time); 16 files build a clip with ffmpeg per test (393 s); 36 files sleep for fixed seconds (514 s); 258 files
use `setUp` and 24 `setUpClass`; `TempLibrary` builds a library per test with no template copy. 85 files over 10 s own 76% of
the time, and a file is the smallest unit the runner schedules, so one 197 s file bounds the wall time however many cores
run. The redundancy found is in fixtures (about 10 of 20 clip files each build their own clip and library), not in
assertions; no file is named for a review round. So the first gain is not deleting tests: it is building each photo, clip
and library once and copying it.

## The rule for removing a test (owner, 2026-11-24)

Keep every **outcome** that is verified, not every test. A test may be deleted or merged when another test verifies the same
outcome better or more broadly; an outcome verified nowhere else is never dropped, only moved to a cheaper layer. A removal
is shown by the per-test coverage map (below) and the owner's charter before and after, and named in its commit message.

## Mechanisms: the ONE place each lives

| Mechanism | The ONE place it lives | Owner | New or existing |
| --- | --- | --- | --- |
| Run files, tiers, per-owner, changed-file, per-test timings | `tools/run_tests.py`, `tests/tiers.py` | Integration | existing, extended |
| A test file's owner and its size tag (pure, sqlite, subprocess, browser) | `tests/owners.py` | Integration | existing, extended |
| A photo or clip made once and copied per test (made by the real writer, ExifTool or ffmpeg, once per run) | `tests/photo_rows.py` successor, one shared corpus module | Files, Media | new; setUp builders call it |
| A migrated library made once, copied per test | `service_fixture.TempLibrary` | Data | existing, extended |
| Waiting for an event, not a fixed sleep | one helper in `tests/` | Integration | new; the watcher and index tests call it |
| Which test covers which line (coverage contexts, generated) | `tools/test_map.py`, output kept under `tests/` | Integration | new; feeds `affected_tests.py` |
| An owner's outcomes and the scenario test for each (charter) | `tests/charters/<owner>.md`, checked by `tests/test_the_test_map.py` | each owner | new |

A test's data is still made by the code that makes the real thing (CLAUDE.md): the shared corpus is built once through the
real writer and copied byte for byte, never faked. Faking ExifTool or ffmpeg at the `ExifToolSession` boundary is a later,
separate step and keeps one real contract test per command shape.

Steady-state writer: a test file added afterwards: which writer keeps the tags, durations and map right with no command
run? The runner records per-test times on every green run; the size tag is derived from the file's imports and a guard fails
the build when a file lacks one or disagrees; the coverage map is regenerated by `tools/test_map.py` and a guard fails when
it is older than the tests it describes.
One-offs: none. The map and timings are generated by the runner, not hand-edited.

## Cuts (each leaves the trunk whole, within the branch budget; each reports a before and after wall time)

1. **See it.** Record per-test and per-file times on every run (green too), prune the 224 stale keys, add `--slowest N`, put
   the node tests in a tier and in the numbers. Gain: none claimed; this makes the others measurable.
2. **Build once, copy per test.** The shared photo and clip corpus and the template library; the five slowest ExifTool
   files (`file_journal`, `a_long_change_cut_off_is_settled_in_chunks`, caption, bake, `tag_a_photo`) and the clip files move
   to it. Largest expected gain (ExifTool and ffmpeg setup is about half of all time); measured here, not assumed.
3. **Wait for events, not seconds.** The 36 sleeping files, starting with `folder_watcher` (23 sleeps) and the index sync tests.
4. **Split what bounds the wall.** A file over about 30 s is cut by scenario or has its setup shared, so the runner's unit is
   small enough to balance 8 jobs; try persistent workers that import the package once only if per-file start cost measures
   high.
5. **Tags and fine-grained runs.** The size tag and a guard; `run_tests.py --owner X --size pure` and a changed-file mode
   from the coverage map; a fast loop of seconds for pure and sqlite tests of one owner.
6. **Charters and the map.** Each owner writes its charter (outcomes and the scenario that verifies each) with the coverage
   map in hand; redundant tests are retired by the rule above, one owner per review; Integration keeps the cross-domain
   scenario layer small and named.
7. **Layers.** Only where a measured file is still slow: the page tests in a lighter DOM (time `jsdom` against `happy-dom` on
   a few of our own page tests first), with the real browser kept for layout, focus and paint; Hypothesis on pure modules
   (paths, vocabulary, dates) where it replaces many examples; no whole-repo mutation testing (needs WSL here).

Order is by measured gain: cut 1, then 2, then re-measure and decide 3 and 4 by what is still slow. Cuts 5 and 6 are what
make it lasting; they are not optional follow-ups. A cut that does not move its measured time says so and is not merged as
a speed claim (docs/DEVELOPMENT.md, "Performance work").

## Not here

A RAM disk, `journal_mode=OFF` (breaks the undo journal), machine-learning test selection, antivirus exclusions (a setting on
the owner's machine; measure by a run with and without, and tell the owner, never change it).
