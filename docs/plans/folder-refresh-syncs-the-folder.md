# Refresh on a folder also syncs it, and a file found gone starts the whole-library sync that removes it
Live count: photo_index holds 55 rows whose file is gone, in 2 folders (`missing_files`, read-only, 2026-11-16). Whole sync 3631 (11:15 to 11:53, 38 min) removed 36; one second after it ended, folder syncs 3632-3634 found 36, 38 and 45 files gone that it never saw (3635 paired 45 as moved), and 26 `sync-folder` rows carry `found_missing > 0` (integration owner, read-only, same day). The Refresh button today (`web/tagpup/library-view.js` `refreshFolderOrView` -> `scanFolder(true)`, `GET /api/folder/scan?force=true`) walks the folder into the page's cache and writes nothing: a gone file stays listed until the daily or catch-up whole sync.
Domains: Integration (`tagpup/jobs/recurring.py`, the route, the job start), Views (the button and its sentence); Files only if `services/sync.py` changes, and nothing here needs it to; integration reviews the seams. Reviewed by the integration owner 2026-11-16: corrections applied below.

Decision (owner, 2026-11-16): Refresh syncs the folder; if that finds a file gone, the whole-library sync is queued. The rule of DECISIONS 2026-10-28 does not change: a sync of ONE folder never removes (a file moved out of it may not have been looked for where it went); only a whole sync removes, after pairing moves and a second walk, root confirmed, never for a folder not looked at (INVARIANTS line 53).

How it fails: share away (the folder sync counts `not looked at`, `missing` is 0, no whole sync is asked, no row touched); Refresh during the daily run (`folder: "running"`, nothing synced, said); a whole sync that started BEFORE the file went and is still walking past that folder will not remove it (the owner presses Refresh again after it ends); naming faces writing (409); Refresh pressed three times (one folder sync at a time through the walk; the whole is claimed once); library switched mid-call (the page drops an answer for another library); a file moved to a sibling folder (a Refresh on the source folder asks for a whole walk, minutes to 38 min on the share, and while it holds the walk the watcher's destination sync is put off; the whole sync pairs the move and the row follows it, through either path); a folder gone (refused as the scan is); a kill mid-request (the folder sync is one journaled change, nothing to settle); the CLI `sync --apply` in another process (the claim row refuses the whole as "running"; the folder sync is not held off, as the watcher's is not today).
