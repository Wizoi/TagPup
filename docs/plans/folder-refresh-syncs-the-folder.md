# Refresh on a folder also syncs it, and a file found gone starts the whole-library sync that removes it
Live count: photo_index holds 55 rows whose file is gone, in 2 folders (`missing_files`, read-only, 2026-11-16); its last one-folder sync found `missing: 1`, removed 0, and the last time it was in step was hours earlier (`sync_state`, same day). The Refresh button today (`web/tagpup/library-view.js` `refreshFolderOrView` -> `scanFolder(true)`, `GET /api/folder/scan?force=true`) walks the folder into the page's cache and writes nothing; it never reaches the index, so a gone file stays listed until the daily or watcher-catch-up whole sync (facts counted from the code, 2026-11-16).
Domains: Files (the sync service and its one-walk lock), Integration (the route, the job start), Views (the button and what it says); integration reviews the seams

Decision (owner, 2026-11-16, asked and answered): Refresh syncs the folder; if that finds a file gone, the whole-library sync is queued. The rule of DECISIONS 2026-10-28 does not change: a sync of ONE folder never removes (a file moved out of it may not have been looked for where it went); only a whole sync removes, after pairing moves and a second walk, root confirmed, never for a folder not looked at (INVARIANTS line 53).

Not built: the library-view Refresh (`refreshLibraryView`) stays as it is (it reads the library; a folder is not what it shows); no progress bar for the whole sync (the Activity page's jobs list shows it, `/api/activity/now`); no new sync mode; no change to what any sync removes.

Steady-state writer: a gone file's row is removed by the whole sync, as today (daily job, watcher catch-up); Refresh only asks for it sooner. A photo added or changed afterwards is kept right by the watcher and the folder sync, with no command run. No command is run by the owner.
One-offs: none. The 55 rows now missing clear on the first whole sync after the build.
How it fails: share away (the folder sync counts it `not looked at`; no whole sync is asked, no row touched), naming faces writing (waited, say so), a whole sync already running (say so, ask nothing), Refresh pressed three times (one folder sync at a time through the walk; the whole is asked once), the owner switching library mid-call (the answer is for the library it was asked of; the page drops an answer for another), a file moved into another folder (the whole sync pairs it, the row follows it), the owner pressing Refresh on a folder that is gone (refused as the scan is).
Tests (scenarios): a Refresh of a folder with one file gone and one new queues the new file's folder and asks for the whole sync once, removes nothing itself; a second Refresh within the hour asks nothing; a folder on a share that does not answer removes and asks nothing; naming faces writing gives "waited"; a file moved to a sibling folder keeps its row after the whole sync; the page says the sentence for each answer.
