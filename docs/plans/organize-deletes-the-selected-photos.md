# Organize deletes the selected photos: in a folder opened on disk, the owner selects photos and clips, clicks Delete, and the same delete a library view runs (the question, the token, the Recycle Bin rules, the batch strip, Cancel, the Activity listing) removes exactly those files and their rows
Live count: an Organize selection is at most 400 photos (photo_index 60,139 photos in 2,572 folders, median 14, p99 146, max 400; kr-track max 387; renton_parkrun max 202; counted read-only 2026-11-16). Nothing is automatic: a delete is a click, a question naming the server's count, OK. Just-look folders (the library holds no row of them): the selection Delete is shown inert with a sentence; the panel's one-photo Delete stays (owner, 2026-11-16: the same job, which deletes rows).
Domains: Views (`services/selection.py`, `web/tagpup/bulk-edit.js`, `selected.js`), Files (`photos.delete`, existing, untouched), Integration (the route contract, the Organize page shell and the scenario tests); integration reviews the seams.
Owner's decisions (2026-11-16): the SAME job as the library view's delete, not a loop over `/api/photo/delete`; the SELECTED photos only (the open photo keeps its own Delete).

Alternative weighed and not taken: putting `id` on every scan record so Organize sends `{ids}`. It would make the page hold two names for one photo, bump `CACHE_VERSION` (every kept scan re-read), and a kept record could name an id the library no longer has while the file is there; the paths kind sends what Organize already sends to bulk-tags.

Steady-state writer: none to keep: a delete removes; a photo added afterwards is the indexer's and the watcher's as today, and a folder opened again is scanned from the rows. The page's kept scan is rewritten by the scan the delete ends in; the server's by the counter.
One-offs: none.

Fails how. A photo changed or gone between the click and the delete: the paths are resolved to ids at the question and again at the start; a re-indexed, deleted-and-synced or moved file gives different ids and the start is 409 CHANGED, nothing deleted ("click Delete once more", as a view does). A path no row has (copied in, not yet indexed): `missing`, never deleted, said in the question ("N of the M selected are not in the library (not indexed yet) and are left where they are"); all missing is "Nothing to delete". A share that does not answer: an error entry (`AWAY_WHY`), untouched, the others go on. Two deletes at once: one page refuses the second by `bulkBusy`; from two pages or beside a view's delete the server's `batches.claim` queues it, and the token refuses the one whose photos the first took. Cancel part way: after the chunk; the reply names what went and what did not; the scan shows the rest. The folder re-scanned or another folder opened while the job runs: the request goes on server side; the follow checks `state.scannedFolder` is still the folder asked (#532) and otherwise forgets that folder's kept scan and touches nothing of the open folder; a library switch mid-delete shows nothing of the first library. A clip the panel plays among the selection: stopped before the request, played again only when the scan still lists it. The open photo with typed edits among the selection: asked about before anything is sent; Cancel stops the delete. Tag changes waiting for a selected photo: refused with a sentence before the question. A kill mid-delete: each file whole or not at all (`photos.delete`: the file first, the rows once the file is); the next scan shows what is left. An update mid-delete: the drain waits for the batch's chunk. The owner sees the batch strip ("deleting 37 photos", Cancel), the status line, the end sentence with for-good counts, the folder's list shorter, the next photo open.
